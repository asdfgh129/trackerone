## ADR-001 · 新建独立 App

**背景**

现有 Client 与 Manager 技术栈一致、代码量小，但产品身份、权限、Firebase、偏好键均冲突；直接合并会继承历史包袱。

**决策**

新建 `trackerone` 工程，以 Client 的跟踪能力与 Manager 的查看能力为参考，重新组织架构与体验。

**理由**

- 可自由选择包名、品牌、Firebase 项目；
- 清理 WebView、键名冲突、两套初始化；
- 以新 App 身份发布，避免旧包名的迁移死结；
- 旧项目可作为功能参考与回归对照。

**后果**

- 需要重新建立商店条目与用户；
- 无法复用旧 App 的安装量；
- 跟踪核心仍可复用 SDK，成本可控。

## ADR-002 · v1 沿用 Traccar Server

**决策**

不重写后端，直接对接 Traccar 6.x REST + WebSocket + OsmAnd 上报。

**理由**

- 服务端能力完整（设备、位置、事件、报表、指令、权限）；
- 避免重复造轮子；
- 用户已有自建/托管服务器。

**后果**

- 受服务端 API 与版本限制；
- 推送依赖服务端 Firebase 配置；
- 多租户/复杂编排需等 v2 BFF。

**触发重新评估**：需要多租户计费、跨服务器聚合、复杂推送编排时。

## ADR-003 · 默认使用 `traccar_client_sdk`

**决策**

跟踪引擎默认实现为 SDK 适配器，业务层依赖 `TrackingEngine` 接口。

**理由**

- Apache-2.0，KMP 原生实现；
- 内置 SQLite 队列、停驶检测、开机恢复、前后台保活；
- 与 Traccar 上报协议一致；
- 旧 Client 已验证。

**后果**

- SDK 可定制性有限；
- 需要真机验证各 ROM；
- 发布前确认第三方许可（旧项目中的 Transistorsoft 元数据不应盲抄）。

**备选**：自研（geolocator + foreground task + drift），预计 +4–6 周。

## ADR-004 · 中国大陆首发使用高德地图

**日期**：2026-11-01
**状态**：已接受

**背景**

首发市场为中国大陆。可选地图：百度、高德、腾讯。三者都需要甲级测绘资质底图，
但坐标系统与 Flutter 生态差异明显。

**决策**

使用高德 `amap_map 1.0.15`（Apache-2.0），GCJ-02 渲染；腾讯作为备选；
百度不采用。

**备选方案**

| 方案 | 结论 |
|---|---|
| 高德 `amap_map` | ✅ 采用：维护活跃、许可证干净、文档完整 |
| 腾讯 `flutter_tencent_map` | 备选：坐标同为 GCJ-02，切换成本低 |
| 百度 | ❌ 排除：BD-09 二次偏移 + 无官方 Flutter 插件 |
| flutter_map + OSM | 仅海外 / 自托管 / 无 Key 兜底 |

**理由**

- 高德与腾讯同为 GCJ-02，未来换供应商**不需要改数据层与业务层**；
- 百度 BD-09 会让轨迹回放、点选建围栏、导出多一层转换，收益不足；
- `amap_map` 是三者中唯一活跃维护的官方风格插件。

**后果**

- 必须接入隐私授权（先同意后初始化），否则商店隐私检测不过；
- Key 与包名/Bundle ID 绑定，换包名需重新申请；
- 地图能力受限于高德 SDK（聚合需自行实现）；
- 海外版本仍需 `flutter_map` 或其他供应商。

**触发重新评估**：高德配额/商务条款不可接受；或需要海外统一底图。

## ADR-005 · Riverpod

**决策**

使用 Riverpod 管理状态与依赖注入。

**理由**

- 编译期安全、可测试、无 BuildContext 依赖；
- `AsyncValue` 适配"缓存 + 刷新"；
- 易在测试中 override。

**后果**

- 团队需熟悉 Notifier/Provider 模式；
- 避免过度使用全局 Provider。

---

## ADR-006 · 原生替代 WebView

**决策**

地图、设备、历史、事件、设置均原生实现；WebView 仅作为 v2 复杂报表兜底。

**理由**

- 原生手势、离线、推送、深链体验更好；
- 避免 JS Bridge 协议与 Web 端耦合；
- 降低安全面（无任意 Web 内容）。

**后果**

- 开发量大于套壳；
- 复杂管理功能（用户/分组/通知规则）延后；
- 需要自行实现报表导出。

---

## ADR-007 · drift

**决策**

本地缓存与队列使用 drift（SQLite）。

**理由**

- 类型安全、可迁移、可测试；
- 支持复杂查询（时间范围、聚合、去重）；
- 与 Flutter 生态成熟。

**后果**

- 需要 build_runner；
- 数据库迁移需谨慎（版本化）。

---

## ADR-008 · 极光 + 厂商通道 + 自建网关

**日期**：2026-11-01
**状态**：已接受（替代「统一使用 FCM」）

**背景**

中国大陆 Android 无 GMS，FCM 拿不到 Token 且长连接会被厂商清理；
Traccar 的 `firebase` notificator 依赖 Google 服务账号，无法用于国内生产。

**决策**

- App：`PushGateway` 接口，中国大陆实现 `JpushPushGateway`；
- 服务端：Traccar 增加 `NotificatorWebhook`，事件 POST 到自建网关；
- 网关：鉴权（HMAC）、别名映射、幂等、限流、模板、回执，调用极光 REST；
- 极光：聚合小米/华为/OPPO/vivo/荣耀厂商通道；
- FCM：仅 `prod-intl` 与开发包保留。

**理由**

- 厂商通道是国产 ROM 锁屏后唯一可靠的到达方式；
- 网关隔离了供应商，换极光只需改网关；
- 不把极光 Master Secret 放进 Traccar 配置或客户端；
- 按 `alias` 推送，不再往 Traccar 用户属性写 Token。

**后果**

- 需要维护 Traccar 自建补丁（升级需重新应用）；
- 厂商通道需要企业主体与 1–2 周资质申请；
- 新增一个服务（网关）与运维成本；
- 个人主体到达率会下降，需在文案中说明。

**备选**：个推/友盟（改网关适配器）；网关轮询 `/api/reports/events`（不改 Traccar，但有延迟）。

## ADR-009 · 独立包名与品牌

**决策**

使用自有包名（占位 `com.example.trackerone`）与品牌，不使用 `org.traccar.*`。

**理由**

- 避免与官方 App 冲突；
- 便于白标与多产品线；
- 合规与商标风险可控。

**后果**

- 不能复用旧 App 的安装与评分；
- 需自行申请 Firebase、签名、商店条目；
- 需要品牌资源（图标、名称、隐私政策）。

## ADR-010 · 坐标与单位

**决策**

数据层统一 WGS-84；速度统一转换为 m/s 供 UI（服务端为 knots）；中国大陆地图在渲染层转 GCJ-02。

**理由**

- 服务端与大多数协议使用 WGS-84；
- 避免坐标转换污染缓存与导出；
- 单位换算集中管理，减少错误。

**后果**

- 高德/百度场景需维护转换与偏移校正；
- 导出 GPX 必须使用 WGS-84。

---

## ADR-011 · 国际化

**决策**

使用 Fluttergen/ARB，继承 Client 的 35 种语言，新增文案全部走 ARB。

**理由**

- 现有翻译资产可复用；
- 避免硬编码；
- 支持 RTL 与动态字体。

**后果**

- 新增文案需翻译流程；
- 长文本布局需测试。

---

## ADR-012 · v1 不引入业务 BFF

**决策**

客户端直连 Traccar Server；不搭建业务中间层（不代理 REST/WebSocket）。

**例外**

推送网关（ADR-013）是唯一新增服务，只处理推送，不代理业务 API。

**理由**

- 降低部署与运维成本；
- v1 用户规模不需要；
- 服务端 API 已满足需求。

**后果**

- 推送编排、多租户、审计能力受限；
- 服务端地址暴露给客户端（可接受）；
- v2 若引入完整 BFF，需保持 API 兼容层。

---

## ADR-013 · 新增轻量推送网关

**日期**：2026-11-01
**状态**：已接受

**决策**

新增一个只做推送的服务（BFF-lite），作为 Traccar 与极光之间的唯一出口。

**职责边界**

| 做 | 不做 |
|---|---|
| 接收 Traccar webhook | 不代理 REST / WebSocket |
| 校验 HMAC、幂等、限流 | 不存业务数据 |
| alias → 用户映射 | 不做账号体系 |
| 模板与多语言 | 不做报表 |
| 调极光、收回执 | 不做设备管理 |

**理由**

- 隔离推送供应商与密钥；
- 统一去重、免打扰、合并；
- 支持多 Traccar 服务器与多租户；
- 未来可平滑切个推/友盟。

**后果**

- 多一个部署单元与监控项；
- 需要设计别名注册接口与鉴权；
- Traccar 需打补丁（见 `server/`）。

## ADR-014 · 中国大陆合规基线

**日期**：2026-11-01
**状态**：已接受

**决策**

把合规作为功能需求而非上线前补丁：

1. 首次启动隐私政策 + 同意流，未同意不初始化任何第三方 SDK；
2. 后台定位单独同意（行踪轨迹属于敏感个人信息）；
3. 应用内提供个人信息收集清单、第三方 SDK 清单、删除入口；
4. 「关于」页展示 APP 备案号与地图审图号；
5. 中国大陆包不初始化 Firebase；
6. 权限按「通知 → 前台定位 → 用户主动开启 → 后台定位」分阶段申请。

**理由**

- 应用商店隐私检测会实际抓包验证初始化顺序；
- 备案是上架前置条件；
- 违规成本高于开发成本。

**后果**

- 首次启动多两步（隐私政策、模式选择），转化率需监控；
- 地图/推送 SDK 必须通过统一入口初始化，禁止绕过 `TrackerMapView`；
- 需要维护 SDK 清单，新增依赖时同步更新。

---

## ADR-015 · 包名仅用于开发

**日期**：2026-11-01
**状态**：已接受

**决策**

开发期使用 `com.example.trackerone`；**发布前必须替换为真实反向域名**
（例如 `com.yourcompany.trackerone`）。

**理由**

- `com.example.*` 是保留示例域，部分商店直接拒绝；
- 包名/Bundle ID 发布后不可更改；
- 高德 Key、极光 AppKey、Firebase 应用都与包名绑定。

**后果**

- 更换包名需同步：`applicationId`、`namespace`、iOS Bundle ID、
  高德 Android/iOS Key、极光应用、Firebase 应用、深链 scheme；
- 建议在 M0 结束前完成，避免后期返工。
