# 00 · 项目章程

## 1. 背景

Traccar 生态目前把移动端拆成两个独立应用：

- **Traccar Client**：把手机作为 GPS 设备，向服务端持续上报位置；只负责"采集 + 上报"。
- **Traccar Manager**：用 WebView 加载 Traccar Web 控制台，负责"查看 + 管理"。

两者服务同一批用户，却存在明显的体验断点：

| 断点 | 现状 | 影响 |
|---|---|---|
| 两个 App | 看自己的位置要装 Client，看设备列表要装 Manager | 用户需要装两个应用、维护两套配置 |
| 两套服务器地址 | Client 填上报地址（`:5055`），Manager 填 Web 地址（`:8082`） | 普通用户难以理解，容易配错 |
| Manager 是 WebView | 地图、列表、报表全部依赖 Web 前端 | 手势、推送、离线、深链体验受限 |
| 无原生实时通道 | Manager 依赖 Web 端的 WebSocket 封装 | 弱网重连、后台恢复不可控 |
| 配置入口割裂 | Client 扫码/URL 配置，Manager 登录后配置 | 无法"一次配置，两处生效" |
| 代码重复 | Firebase、偏好、存储、深链各写一套 | 维护成本翻倍 |

本项目不复用两个旧 App 的包身份，而是**新建一个产品**，把两条能力线合并到一个原生应用里，并补齐实时性、离线、可诊断性和合规能力。

## 2. 产品愿景

> 一个 App，既能上报这台手机的位置，也能实时查看所有设备。

用户打开应用后：

1. 连接自己的 Traccar 服务器；
2. 一键把本机注册为设备并开始后台上报；
3. 在地图上看到本机和其他设备的实时位置；
4. 回看轨迹、接收告警、发送指令；
5. 全程清楚知道"是否在上报、上报到哪里、为什么失败"。

## 3. 目标与非目标

### 3.1 目标

| 编号 | 目标 | 衡量方式 |
|---|---|---|
| G1 | 一个 App 完成"上报 + 查看" | 核心流程不依赖第二个 App 或 WebView |
| G2 | 本机上报可靠 | 24h 心跳可用率 ≥ 95%，断网不丢点 |
| G3 | 实时地图体验原生 | 位置更新端到端 P95 < 10s，地图 60fps |
| G4 | 配置一次到位 | 服务器档案同时驱动 API 与上报，配置步骤 ≤ 3 步 |
| G5 | 可诊断、可恢复 | 用户可在应用内定位 80% 的跟踪失败原因 |
| G6 | 可白标、可多服务器 | 品牌与服务器地址可配置，不写死 |
| G7 | 符合中国大陆上架要求 | APP 备案号可用；隐私检测通过；地图/推送使用合规供应商 |

### 3.2 非目标（v1 不做）

- 不重写 Traccar 服务端，不做自有后端/BFF。
- 不做 Web 管理后台（用户管理、复杂报表编辑仍在 Web 端）。
- 不做视频流、车载硬件、调度派单、计费。
- 不做 Wear OS / 桌面端。
- 不做社交、轨迹分享社区。
- 不做账号体系（沿用 Traccar 用户体系）。

## 4. 目标用户与场景

### 4.1 用户画像

| 画像 | 需求 | 关键功能 |
|---|---|---|
| 个人/家庭 | 看孩子/老人/自己的位置 | 本机上报、实时地图、围栏告警 |
| 车队管理员 | 看多车位置、历史、告警 | 设备列表、轨迹回放、事件推送 |
| 外勤/资产 | 手机作为追踪器，长期在线 | 省电模式、开机恢复、离线缓存 |
| 白标经销商 | 换品牌、换服务器、批量分发 | 品牌配置、MDM/二维码、远程配置 |

### 4.2 核心场景

1. **首次使用**：下载 → 选择"跟踪本机 / 查看设备 / 两者都要" → 填服务器 → 登录 → 授权定位 → 开始上报。
2. **日常查看**：打开即地图，看到所有设备最新位置；点击设备看详情与今日轨迹。
3. **轨迹回放**：选日期 → 播放 → 看速度/停留 → 导出 GPX。
4. **告警响应**：收到围栏/超速推送 → 点击直达事件位置 → 查看前后轨迹。
5. **故障排查**：上报停止 → 诊断页显示"后台定位被系统限制" → 跳转厂商省电设置。
6. **远程指令**：管理员对设备发送"立即定位/停止上报" → App 收到推送指令（中国大陆走极光 + 厂商通道）并执行/确认。

## 5. 成功指标

### 5.1 北极星指标

**周活跃跟踪设备数（Weekly Active Tracked Devices）**：一周内至少成功上报一次的本机设备数。

### 5.2 关键指标

| 类别 | 指标 | 目标（上线 90 天） |
|---|---|---|
| 激活 | 首次打开 → 开始上报转化率 | ≥ 70% |
| 激活 | 首次打开 → 看到地图转化率 | ≥ 60% |
| 留存 | 7 日留存 | ≥ 30% |
| 留存 | 30 日留存 | ≥ 15% |
| 可靠性 | 24h 心跳可用率 | ≥ 95% |
| 可靠性 | 位置端到端延迟 P95（在线） | < 10s |
| 可靠性 | 崩溃自由用户率 | ≥ 99.5% |
| 性能 | 地图首屏可交互 | < 2s（4G） |
| 性能 | 1000 设备 / 10k 历史点 | 可流畅缩放与回放 |
| 功耗 | 中等配置 24h 电量消耗 | ≤ 6% |
| 成本 | 单用户日均上报请求 | ≤ 300 |

## 6. 范围与版本

### MVP（v1.0，必须）

- 服务器档案（API + 上报地址）
- 账号登录（密码 + Token）、生物识别锁
- 本机设备注册/绑定
- 后台上报（开始/停止/单次/SOS）
- 跟踪配置（精度、间隔、距离、角度、心跳、缓冲、停止检测）
- 实时地图（设备列表、状态、位置、跟随、聚合）
- 设备详情（电量、速度、方向、最后更新、今日轨迹）
- 历史回放（时间范围、播放、速度曲线）
- 事件列表 + 推送（极光/厂商通道，FCM 仅海外）+ 点击直达
- 远程指令（单次定位、开始/停止）
- 设置（单位、主题、语言、隐私、退出）
- 诊断页（权限、队列、最后上报、日志导出）
- 崩溃上报 + 基础分析

### v1.1（增强）

- OIDC / 企业 SSO
- 二维码/MDM 批量配置
- 围栏查看与简单编辑
- 报表（行程、停留、里程汇总）
- 多服务器快速切换
- 地图离线瓦片缓存
- 小组件（跟踪状态/一键 SOS）
- 平板与横屏适配

### v2（按数据决定）

- 自建 BFF（多租户、推送编排、审计）
- 原生管理能力（用户/分组/通知规则编辑）
- 地图供应商切换（MapLibre / 高德 / Google）
- 车机/ Wear OS
- 团队协作与共享

## 7. 约束与依赖

| 类型 | 约束 |
|---|---|
| 后端 | 必须兼容 Traccar 6.x REST / WebSocket；不假设可修改服务端 |
| 平台 | Android 7.0（API 24）+，iOS 15+ |
| 定位 | 后台定位必须符合国内商店 / Google Play / App Store 政策 |
| 地图 | 首发中国大陆使用高德（甲级资质、GCJ-02），数据层保持 WGS-84 |
| 推送 | 中国大陆使用极光 + 厂商通道 + 自建网关；FCM 仅海外/开发 |
| 合规 | 需 APP 备案、域名 ICP 备案、隐私政策 + SDK 清单、软著（按商店要求） |
| 测绘 | 不得自采/自绘地图数据；不得转售瓦片；展示审图号 |
| 品牌 | 不得未经授权使用 Traccar 商标与图标 |
| 团队 | 默认 1 名 Flutter 主程 + 0.5 名后端/QA；排期见 06 |
| 设备 | 需要真机矩阵（含国产 ROM）做后台保活测试 |

## 8. 设计原则

1. **默认安全**：Token 只进 Secure Storage；日志脱敏；最小权限。
2. **离线优先**：地图、设备、历史先读缓存，再增量同步。
3. **状态可见**：任何后台行为都要有 UI 反馈（上报中/已暂停/受限）。
4. **渐进授权**：先前台定位，用户开启上报时再申请后台权限。
5. **可替换**：定位引擎、地图、推送、存储均通过接口隔离。
6. **不造轮子**：上报核心复用 `traccar_client_sdk`，接口层可替换。
7. **可白标**：品牌、服务器、功能开关集中配置。
