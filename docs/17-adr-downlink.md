# 17 · ADR-016 服务端下行消息：推送唤醒 + REST 收件箱

> 状态：已接受（2026-11-19）
> 关联：`docs/08-decisions-risks.md` ADR-016、`docs/12-push-integration.md`
> 实现：App 侧已完成（`lib/features/inbox/`、`lib/core/push/inbox_*`）；网关侧待实现。

## 1. 背景

既有能力只覆盖「设备 → 服务端 → App」的上行与事件通知，服务端无法主动把
**指令、公告、调度消息**可靠地送到某个 App 用户。需求有两类：

1. **设备指令**：调度/管理员要求 App 侧用户确认并执行 Traccar 指令
   （单次定位、断油、重启等），需要可追溯、防重复、可过期；
2. **用户消息**：告警补充说明、运营公告、人与人之间的调度消息。

约束：

- 中国大陆不能依赖 FCM，已在用极光 + 厂商通道（ADR-008/013）；
- 不想为了低频下行再引入一套需要长期运维的 Broker；
- 消息属于敏感个人信息（可能含位置、车牌、调度内容），要支持撤回与本地清理。

## 2. 决策

采用 **「推送唤醒 + REST 收件箱（持久化 + ACK）」**：

```
服务端产生消息
  → 写入收件箱存储（按 userId 归属，带 TTL）
  → 极光推送一条「壳通知」（只带 inboxId，不带正文）
  → App 收到通知/点击/进入消息中心
  → GET  /v1/messages?since=<cursor>&limit=50
  → 本地去重、展示、按需执行指令
  → POST /v1/messages/{id}/ack        （投递回执）
  → 已读仅存本地（不回传）
```

**不引入 MQTT**，也**不新增 WebSocket 协议**。理由：

- 已有 WebSocket（`traccar_socket.dart`）用于位置/事件实时流，再加一条长连接
  只会增加耗电、心跳与重连复杂度；
- 推送负责「叫醒」，REST 负责「补齐」，天然支持离线、进程被杀、换机；
- 消息量级低（人均每天几十条以内），轮询只在打开页面 / 手动刷新 / 推送到达时发生；
- ACK 与 id 去重即可满足「至少一次」投递，不需要 Broker 的会话状态。

## 3. 备选方案

| 方案 | 优点 | 不采用的原因 |
|---|---|---|
| 纯推送带正文 | 实现最简单 | 通知栏泄露敏感内容；离线/被杀后无法补拉；无回执 |
| MQTT / EMQX | 真正的服务端推送、QoS | 多一套 Broker 运维与鉴权；厂商通道仍要推送唤醒；团队无现成运维 |
| 复用现有 WebSocket 下发 | 复用连接 | 仅前台有效；断线期间丢消息；协议要扩展消息类型与 ACK |
| 自建长连接 | 实时性最好 | 与厂商推送重复造轮子，耗电与保活风险高 |

## 4. 接口契约

鉴权：复用 Traccar Token，`Authorization: Bearer <token>`；网关据此校验
用户与消息归属（不得只信客户端传入的 userId）。

### 4.1 拉取

```http
GET /v1/messages?since=<cursor>&limit=50
Authorization: Bearer <token>
```

```json
{
  "messages": [
    {
      "id": "msg_123",
      "kind": "command",
      "title": "指令：断油",
      "body": "调度要求对京A12345 断油",
      "data": {
        "deviceId": 12,
        "command": "engineStop",
        "attributes": {}
      },
      "createdAt": "2026-11-19T10:00:00Z",
      "expiresAt": "2026-11-19T11:00:00Z"
    }
  ],
  "nextCursor": "c_456"
}
```

- `kind`：`command` | `notice` | `chat`，未知值按 `unknown` 展示且不提供操作；
- `since` 缺省表示从最新一页开始；`nextCursor` 为空表示没有更多；
- 服务端按用户过滤，**不得**返回其他账号或已过 TTL 的消息；
- `data.deviceId` 与 `data.command` 决定能否执行，缺失时 App 只读展示。

### 4.2 投递回执

```http
POST /v1/messages/{id}/ack
Authorization: Bearer <token>
```

- 成功返回 `204`/`200` 均可；App 不解析响应体；
- ACK 表示「客户端已收到并持久化展示过」，**不等于已读**；
- ACK 失败时 App 忽略错误，靠下次重发 + 本地 id 去重兜底。

### 4.3 推送壳

```json
{
  "inboxId": "msg_123",
  "title": "新消息",
  "body": "你有一条新的调度消息"
}
```

通知正文不包含车牌、地址、指令详情；点击后按 `inboxId` 进入 `/inbox` 并触发同步。

## 5. 客户端行为

| 场景 | 行为 |
|---|---|
| 未登录 | 不拉取；推送点击先缓存，登录后跳转 `/inbox` |
| 未配置 `PUSH_GATEWAY_URL` | 展示「未配置消息网关」，不报错 |
| 网络失败 | 保留已加载列表，顶部提示可重试；下拉强制刷新忽略游标 |
| ACK 失败 | 忽略，消息仍展示 |
| 重复 id | 按 id 去重，保留最新字段 |
| 消息过期 | `expiresAt < now` 时不提供「执行」，仅展示 |
| 未知指令 | 提示「App 暂不支持该指令类型」，不发送 |
| 破坏性指令 | 二次确认（断油/重启/恢复出厂） |
| 本地清理 | 退出登录、删除服务器、清除数据时清空游标与已读 id |

本地状态：

- 已读 id 按 `serverId:userId` 隔离持久化（`PrefsInboxStore`），最多保留 500 条；
- 游标只保存在内存：冷启动重新拉取最新一页，避免消息正文与增量位置长期落盘；
- 不缓存消息正文；进程重启后由服务端按 TTL 重新下发，已读状态仍能恢复。

## 6. 安全与合规

- 传输必须 HTTPS；网关校验 Bearer Token 与消息归属，禁止越权读取；
- 推送壳与日志不得包含正文、车牌、坐标；网关日志只记录 id 与状态；
- 消息 TTL 由服务端控制（建议指令 1 小时、通知 7 天），过期即删；
- 行踪轨迹属敏感个人信息：消息中如含位置，按最小必要原则下发；
- 用户撤回总隐私授权或注销账号时，服务端删除该用户消息，App 清空本地状态；
- 指令执行仍走既有 `commandProvider`，保留队列、重试与审计，不因收件箱绕过确认流程。

## 7. 升级触发条件

出现以下任一情况时，重新评估引入 MQTT / 长连接下行：

1. 单用户持续下行 > 1 条/分钟，或需要端到端 < 2 秒的聊天体验；
2. 需要服务端感知「在线状态 / 正在输入 / 已读回执」等会话能力；
3. 推送配额或厂商通道送达率成为瓶颈，且消息不能等下一次前台同步；
4. 需要广播/群发到大量在线用户且要保证顺序。

升级时保留本契约（收件箱仍作为持久化与补偿通道），只把「唤醒」换成
长连接事件，避免一次性推翻客户端。
